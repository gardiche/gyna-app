# Gyna — contexte pour Claude Code

Gyna est l'agent d'acquisition (GTM) d'Alpact, venture builder en Savoie. Les trois associés lui confient des missions dans un chat ; Gyna orchestre cinq sous-agents : Sourcing, Qualification et Rédaction trouvent des prospects LinkedIn, jugent leur chaleur et rédigent une première approche ; Veille analyse les concurrents et leurs publicités ; Ads crée des publicités ; Campagnes prépare leur mesure et leur diffusion, et propose où mettre le budget. **Rien ne part vers l'extérieur sans la validation d'un associé.** Outil interne aujourd'hui, pensé pour être commercialisé plus tard (multi-organisation dès le schéma).

Première venture : **L'Amorce** (bootcamp, objectif 10 à 15 apprenants).

Le README décrit l'architecture et l'installation pas à pas. Ce fichier résume les décisions et l'état du projet. La direction produit (état des lieux, questions à trancher, cible) est dans `docs/produit.md` : la relire avant de reprendre ou d'ajouter une fonction.

## Langue et ton

- Échanges avec Thomas : en français, tutoiement.
- Tout ce que l'app ou les agents produisent pour l'extérieur (messages aux prospects) : vouvoiement.
- Textes d'interface : français, phrases complètes et sobres.

## Architecture

```
Navigateur ─▶ App Next.js (Vercel) ─▶ Pont Gyna (VPS) ─▶ hermes serve (VPS, profil « gyna »)
                    ▲                                         │
                    │ temps réel                              ▼
                 Supabase ◀──────── Serveur MCP Gyna ◀── agents + Apify
```

- Monorepo pnpm 10 + Turborepo, TypeScript, Zod (`packages/schemas`).
- `apps/web` : Next.js 15 App Router sur Vercel, Supabase (Auth email + mot de passe, RLS, Realtime). Déploiement automatique à chaque push sur `main`.
- `apps/bridge` : Fastify + WebSocket JSON-RPC vers `hermes serve` (127.0.0.1:9119). Requêtes app→pont signées HMAC (`x-gyna-ts`, `x-gyna-signature`), réponses en SSE, callback `POST /api/bridge/turn-complete` pour enregistrer la réponse finale.
- `apps/mcp` : serveur MCP (HTTP streamable, Bearer `MCP_ACCESS_TOKEN`), **seul chemin d'écriture des agents vers la base**, via le rôle Postgres `gyna_mcp`. Chaque appel porte un `mission_token` qui fixe org, mission et budget : une clé courte `gm-xxxxx-xxxxx-xxxxx-xxxxx` créée par l'app à chaque mission (seule son empreinte est en base, `missions.token_hash`, valable 6 h). Le JWT d'origine, trop long, était mal recopié par les agents et refusé par le MCP ; il reste accepté pour compatibilité.
- Hermes v0.21.5, serveur dédié au profil (`hermes -p gyna serve --isolated` : sans cela les appels hors session, comme `image.generate`, lisent le profil par défaut de la machine), profil `gyna` dans `/root/.hermes/profiles/gyna` (`SOUL.md` = `infra/hermes/agents/gyna.md`). Modèle par défaut : `gpt-6-sol` via `openai-codex` ; modifiable par conversation dans l'app. Les sous-agents peuvent tourner sur un modèle plus léger : `GYNA_SUBAGENT_MODEL=<identifiant> bash infra/hermes/setup-hermes.sh` écrit `delegation.model` dans le profil (un seul modèle pour tous les sous-agents, Hermes ne permet pas d'en choisir un par délégation) ; le modèle choisi dans l'app ne vaut alors plus que pour Gyna.

## Décisions prises

- Hermes est le moteur, l'interface est la nôtre. Les associés n'utilisent pas l'interface Hermes.
- Délégation asynchrone : dans `hermes serve`, `delegate_task` tourne en arrière-plan et Hermes relance Gyna dans un nouveau tour quand ses sous-agents ont fini (pas de réglage pour forcer le synchrone). Le pont suit chaque mission au-delà du premier tour (`apps/bridge/src/missions.ts`) : événements `subagent.start`/`subagent.complete` → `POST /api/bridge/activity` (journal), tours de suite → `POST /api/bridge/turn-complete` avec `followup` ; la mission reste « running » et la session verrouillée tant qu'un sous-agent travaille ou qu'une délégation attend son résultat (30 min sans nouvelles : mission close). Gyna préfixe chaque goal par `[Sourcing]`, `[Qualification]` ou `[Rédaction]`. L'app reçoit messages et journal en temps réel.
- Jeton de mission glissé par Hermes (décision du 19/10/2026, après un jeton mal recopié par Ads : appel refusé, puis serveur MCP suspendu par Hermes) : le plugin Hermes `gyna-mission` (`infra/hermes/plugins/gyna-mission`, hooks `pre_llm_call`, `subagent_start`, `pre_tool_call`) lit le jeton dans le bloc [Mission Gyna], le transmet aux sous-agents par le lien parent → enfant et l'impose dans les arguments de chaque appel `mcp__gyna__*`. Ce que l'agent recopie ne sert plus que si la session n'a pas de jeton connu (Hermes redémarré en cours de mission). Installation, sonde et retrait : `bash infra/hermes/mission-plugin.sh install|probe|report|stop|remove` ; tests : `python -m unittest discover -s infra/hermes/plugins/gyna-mission -p "test_*.py"`. Les jetons sont aussi masqués (`maskMissionTokens`) dans le journal, le chat et le flux du pont.
- Sous-agents : éphémères, lancés par Gyna avec `delegate_task`. Leur rôle est dans les fiches de `infra/hermes/agents/` (recopiées dans `gyna.md`). Pas de profil Hermes séparé pour l'instant ; à reconsidérer si on veut un modèle, des outils ou une conversation directe par agent. Paperclip écarté : il ferait doublon avec l'app (budgets, validations, journal).
- Skills : rédigés et versionnés dans l'app (page Skills), **attribués à un agent** (`skills.agent`, null = tous les agents) et activables. Chaque agent les charge avec l'outil MCP `get_agent_skills`. La mémoire des agents, c'est ce qui est écrit dans les skills et en base, pas une mémoire Hermes.
- Contenu des skills : relu dans le dépôt (`packages/db/seed/skills/*.md`, format Objectif / Entrées / Méthode / Sortie / Garde-fous / Exemples, description « ce que fait le skill et quand l'utiliser » à la troisième personne, évaluations dans `evaluations.md`), chargé en base avec `node packages/db/scripts/skills-to-sql.mjs` (nouvelle version seulement si le contenu change). Ce qui dépend d'une venture va dans son brief, pas dans un skill.
- Brief GTM par venture, versionné dans l'app ; source relue dans `packages/db/seed/briefs/<venture>.md` (champs du brief, objectif, fenêtre, segments), chargée avec `node packages/db/scripts/brief-to-sql.mjs <venture>`. L'Amorce : programme d'entrepreneuriat de 16 semaines (25/01 → 14/05/2027, Annecy), cible porteurs de projet, créateurs, entrepreneurs et salariés qui veulent entreprendre, en Auvergne-Rhône-Alpes et à Genève ; pour Gyna, « inscrit » = pré-inscription sur amorce-campus.fr ; objectif 50 pré-inscriptions avant la clôture du 15/11/2026 (repoussée le 19/10) ; consigne : du volume, brouillons pour les chauds et les tièdes.
- Chaleur : froid / tiède / chaud sur une fenêtre de 60 jours ; « chaud » exige un signal récent et sourcé.
- Qualification en deux temps (décision du 16/10/2026 ; avant, 42 prospects qualifiés tous froids, faute de publications lues) : le **tri** (`fetch_profiles` lit le profil complet, 0,004 $ par profil, et calcule les faits : mois comme fondateur, poste salarié en cours, années de carrière ; `triage_prospects` note l'adéquation A, B, C ou écarte, selon la grille « Adéquation » du brief ; skill `trier-les-prospects`) suit le Sourcing de lui-même ; la **qualification fine** (`fetch_posts` lit les publications de la fenêtre du brief, 10 au plus, sans repartages, 0,002 $ chacune, sur les A par défaut ; puis `add_signals` et `qualify_prospect`) se fait à la demande d'un associé. Code dans `apps/mcp/src/linkedin-profiles.ts` ; colonnes `prospect_ventures.fit`, `fit_reason`, `triaged_at`, `prospects.facts`, `profile_fetched_at`, `posts_fetched_at` ; un profil lu depuis moins de 30 jours n'est pas relu. Page Prospects : filtre et colonne « Adéquation », tri par adéquation puis chaleur.
- Relire et exporter les prospects (décision du 20/10/2026, après un tri que Gyna ne pouvait ni relister ni exporter) : outil MCP `list_prospects` (lecture seule, filtres adéquation, chaleur, dates d'ajout, 300 lignes au plus ; Gyna l'appelle elle-même et en tire ses comptes rendus chiffrés, plutôt que d'additionner les comptes rendus des délégations) ; bouton « Exporter en CSV » de la page Prospects (`GET /api/prospects/export`, mêmes filtres que la page via `apps/web/src/lib/prospects-query.ts`, statut « Tous, écartés compris », point-virgule et BOM pour Excel). Les agents ne créent pas de fichier.
- Données LinkedIn via Apify uniquement, sans cookies de compte personnel.
- Sourcing en un appel (décision du 16/10/2026, après des sourcings trop restrictifs) : l'outil MCP `search_linkedin_profiles` (`apps/mcp/src/linkedin-search.ts`) lance lui-même l'acteur `harvestapi/linkedin-profile-search` en mode court, avec des réglages fixés par le code (intitulés actuels, lieux, filtres facultatifs « moins d'un an dans l'entreprise » , taille d'entreprise `company_sizes` et secteur `industries`, dont le nom exact se trouve avec `find_linkedin_industries` ; table des secteurs dans `apps/mcp/src/industries.ts`), enregistre tous les profils exploitables et déclare le coût ; le budget de la mission est vérifié avant le lancement. L'agent ne trie plus rien. Variable `APIFY_TOKEN` dans `/etc/gyna/mcp.env` (même jeton que le serveur MCP Apify du profil).
- Ventures dont la cible est un établissement (décision du 28/10/2026, Pressy Services : pressings, pros du linge) : sourcing en données brutes d'entreprises autour d'un lieu, pas de profils LinkedIn. Outil MCP `search_places` (`apps/mcp/src/places.ts`, acteur Apify `compass/crawler-google-places`, sans cookies ; lieu géocodé par OpenStreetMap, rayon en km, 0,005 à 0,01 $ par lieu, coût relevé après coup et à vérifier dans la console Apify) ; table `companies` (migration 0032, dédoublonnée par `place_id` et venture ; nom, catégorie, adresse, téléphone, site, note, avis). Le tri devient le jugement du **potentiel de linge** (`list_companies`, `rate_companies` : fort, possible, faible, écarté), volontairement large, fait par la Qualification à la demande d'un associé une fois les données vues. Brief `packages/db/seed/briefs/pressy-services.md` (v2, 9 segments, ouvert : les segments ne sont qu'une liste de départ). Pas de page ni d'export CSV des entreprises pour l'instant. Aucune prospection à froid en masse avant validation juridique.
- Budget plafonné par mission ; au-delà, la mission attend l'accord d'un associé.
- Outils du profil `gyna` en liste blanche (`setup-hermes.sh`) : `delegation`, `todo`, `web`, `vision` (visuels des pubs, pour la Veille) et les serveurs MCP ; `hermes serve` utilise la plateforme `cli`. Mémoire Hermes coupée. `desktop_project` (toolset `project`, injecté par `hermes serve`) laissé : inoffensif sans fichiers ni terminal. Les sous-agents ne peuvent pas avoir plus d'outils que Gyna. Rouvrir un outil : `hermes -p gyna tools enable <nom>` et l'ajouter à `KEEP_TOOLSETS`.
- Mémoire des sous-agents : en base, pas dans Hermes. Les brouillons gardent le texte proposé (`drafts.original_body`, figé par trigger), le texte final corrigé par un associé (`body`) et la raison du refus (`rejection_reason`). L'outil MCP `get_feedback` les rend à la Rédaction et à la Qualification avant chaque tâche.
- Faire évoluer un agent : on le demande à Gyna dans le chat. Elle appelle `propose_skill_update` (contenu complet + raison) ; la proposition (`skill_proposals`) passe par « À valider » avec l'avant et l'après, et ne crée la nouvelle version du skill qu'après l'accord d'un associé. Les fiches des agents (outils, ordre de travail, sécurité) restent dans le code et ne se modifient pas par un skill.
- Page de chaque agent (`/agents/[clé]`) en lecture seule : la fiche affichée est celle de `infra/hermes/agents/*.md`, intégrée au build de l'app (règle webpack `asset/source`, entrées turbo). Équipe listée sous les conversations, dans la colonne de gauche du chat.
- Veille concurrentielle : agent `veille` (fiche `infra/hermes/agents/veille.md`, skills `profiler-un-concurrent`, `decortiquer-les-pubs`, `synthese-de-la-veille`). Tables `competitors` (fiche markdown observé / déduit / implications), `competitor_ads` (texte tel quel et analyse : angle, accroche, promesse, public ; dédoublonnées par lien de la bibliothèque) et `watch_summaries` (versions en ajout seul). Sources : bibliothèques publicitaires publiques de Meta, LinkedIn et Google via Apify sans cookies, et la recherche web. Visuels lus avec l'outil Hermes `vision`. Aucune performance de pub n'est disponible : une longue diffusion sert d'indice. Page `/veille`.
- Création de pubs : agent `ads` (fiche `infra/hermes/agents/ads.md`, skills `creer-des-pubs`, `modeles-de-pubs`, `accroches-et-titres`). Il part du brief, de la veille (`get_watch_summary`, `get_competitor_ads`) et des retours (`get_ad_feedback`), et soumet des lots avec `submit_ads` : tables `ad_batches` et `ads` (texte proposé figé dans `ads.original`, version corrigée dans les colonnes, raison du refus). Les limites de caractères par plateforme (`AD_LIMITS` dans `packages/schemas`) sont vérifiées par le MCP et dans l'app. Une validation `ad_batch` par lot ; chaque pub se décide sur la page `/pubs` et la validation se clôt quand il n'en reste plus en attente. Visuels : générés à la demande d'un associé (bouton « Générer le visuel » de la page `/pubs`), jamais par l'agent. L'app appelle `POST /images` du pont, qui appelle la RPC Hermes `image.generate` (fournisseur `openai-codex` : `gpt-image-2` par l'abonnement ChatGPT, sans clé d'API ; qualité et taille seulement indicatives) et reçoit l'image en data URL ; l'app la range dans le bucket public `gyna-media` (`ad_images`, plusieurs versions par pub). Cette RPC n'accepte que du texte : les références de la bibliothèque (`venture_assets` : logo, photos, charte, inspirations) entrent dans la consigne par leur description, écrite par l'agent Ads avec l'outil de vision (`get_ad_references`, `describe_ad_reference`), et par la note de l'associé. Passer à GPT Image 2.5 demande une clé d'API OpenAI et `image_gen.provider: openai`. Pas d'accès aux comptes publicitaires, rien n'est publié. Pilotage des campagnes (lecture des performances) : plus tard.
- Posts LinkedIn et Instagram : second mode de l'agent `ads` (skills `ligne-editoriale`, `ecrire-des-posts`, `carrousels`, outil `submit_posts`). Mêmes tables que les pubs (`ad_batches.kind = 'post'`, `author` = page ou associé, `ads.slides` pour les carrousels, `scheduled_for`, `published_at`) et même validation post par post, page `/posts` avec la liste « À publier ». Les limites de chaque réseau (`POST_LIMITS`) sont vérifiées par le MCP. Publication : jamais par un agent. Sur un post approuvé, un associé choisit « Publier maintenant » (avec confirmation) ou une heure (`ads.scheduled_at`, `publish_status`) ; le pont sert d'horloge et appelle chaque minute `POST /api/bridge/publish-due`, qui publie ce qui est dû (`apps/web/src/lib/publish.ts`, verrou par passage à `publishing`). Instagram seulement pour l'instant, par l'API Graph de Meta : posts à une image et carrousels de 2 à 10 diapositives. Variables Vercel `META_ACCESS_TOKEN` et `META_IG_USER_ID` (et `META_GRAPH_VERSION` facultative), posées par Thomas. Un carrousel demande une image par diapositive (`ad_images.slide` : 0 = couverture ou visuel unique, n = diapositive de rang n), générée à partir de son texte ou déposée (`CarouselVisuals`) ; seules les diapositives qui ont une image sont publiées, dans l'ordre (couverture obligatoire, 2 images au moins), et l'app le dit avant la confirmation ; le générateur ne voit pas les autres images, la cohérence de la série tient à la consigne. Un post Instagram part aussi sur la Page Facebook (case « Publier aussi sur la Page Facebook », cochée par défaut dès que la Page est reliée ; un post déjà publié sur Instagram seulement se rattrape d'un clic, `POST /api/pubs/[id]/facebook`, `ads.also_facebook`, `facebook_url` ; variable Vercel `META_PAGE_ID`, autorisation `pages_manage_posts` sur le jeton) : Facebook est publié après Instagram, et son refus est signalé sur le post sans défaire la publication Instagram. LinkedIn : copie manuelle puis « Marquer comme publié ». Les visuels d'un lot se génèrent d'un clic (`BatchVisuals`), et un visuel fait ailleurs se dépose sur le post.
- Charte de marque par venture (décision du 26/10/2026, après des associés qui tournaient en rond sur le logo et les axes créatifs) : la marque (logo et emplacement, palette, polices, ton, mots et formules interdits, formats par canal, cible, positionnement, mentions obligatoires) vit dans la table `brand_kits` (versions en ajout seul, `BrandKitContent` dans `packages/schemas`, migration 0029), saisie sur la page de la venture (associés seulement), lue par l'agent Ads avec l'outil MCP `get_brand_kit` (hors `PROSPECTION_TOOLS`) comme règles contraignantes. Les skills restent génériques. Source relue : `packages/db/seed/brand-kits/<venture>.md`, chargée avec `node packages/db/scripts/brand-kit-to-sql.mjs <venture>` ; les points non tranchés y restent vides. Finition déterministe (décision du 26/10/2026) : la consigne de génération reprend palette, polices, mentions et un style sobre sans éléments décoratifs ; à l'arrivée de l'image, l'app (`apps/web/src/lib/finish-visual.ts`, sharp) la recadre au format de la charte, pose le vrai logo à l'emplacement prévu (sur une plaque unie si le fond est sombre ou chargé) et relève ses vérifications dans `ad_images.checks` (migration 0030 : recadrage, part des teintes vives proches de la palette, zone du logo, textes), montrées sous le visuel. Les cases « Contrôles automatiques » de la charte (point d'exclamation, émoji, tiret cadratin, prix) et ses mots et formules interdits font refuser un lot par `submit_ads` et `submit_posts`. Générateur d'images : si `OPENROUTER_API_KEY` est posée dans Vercel, la route de génération appelle l'API d'images d'OpenRouter (`apps/web/src/lib/openrouter-image.ts`, modèle `IMAGE_MODEL`, défaut `openai/gpt-image-2`, qualité `IMAGE_QUALITY`, défaut `medium`) avec de vraies images de référence (inspirations cochées) ou, pour « Modifier cette version », l'image brute précédente (`ad_images.raw_url`, migration 0031) ; le coût renvoyé est inscrit au journal. Sans clé, ou en cas d'échec, le pont Hermes génère à partir du texte seul. Limite : les mentions (pastille « 16 semaines ») et le texte du visuel restent dessinés par le générateur, sans vérification de lecture.
- Gestion de campagnes : agent `campagnes` (fiche `infra/hermes/agents/campagnes.md`, skills `plan-de-mesure`, `structurer-les-campagnes`, `piloter-meta`, `piloter-google-et-linkedin`, `bilan-et-recommandations`). Il lit les pubs approuvées (`get_approved_ads`) et les chiffres que l'associé donne dans le chat, et enregistre trois documents versionnés (`campaign_docs` : mesure, plan, bilan ; `save_campaign_doc`, `get_campaign_docs`), affichés page `/campagnes`. Toutes les règles de décision sont des multiples du coût cible par pré-inscription. Hors Meta (Google, LinkedIn) : l'agent propose, un associé décide et applique.
- Pilotage autonome sur Meta (décision de Thomas du 13/10/2026, qui remplace « l'agent propose, un associé applique » pour Meta) : une fois les pubs approuvées et une enveloppe activée par un associé (page `/campagnes`, table `ad_pilots` : budget total, dates, coût visé), l'agent Campagnes lance et pilote seul, avec le serveur MCP officiel de Meta (`https://mcp.facebook.com/ads`, outils `ads_*`, jeton de l'utilisateur système de rôle Employé ; branché sur le profil par `GYNA_META_ADS=1 bash infra/hermes/setup-hermes.sh`, jeton demandé sans affichage). Skill `piloter-en-autonomie`. Garde-fous, du plus sûr au moins sûr : le plafond de dépenses du compte publicitaire, fixé par un associé chez Meta ; l'app elle-même, qui relit la dépense toutes les dix minutes (`POST /api/bridge/pilot-due`, appelé par le pont) et met tout en pause si l'enveloppe est atteinte ou la période finie, et le bouton « Tout mettre en pause » (`apps/web/src/lib/pilot.ts`, variables Vercel `META_ACCESS_TOKEN` et `META_AD_ACCOUNT_ID`) ; les outils MCP `get_ad_pilot` (`may_act`) et `record_ad_launch` (seules les pubs approuvées, `ads.external_id` et `external_status`) ; les consignes de l'agent. Hermes ne permet pas de réserver les outils `ads_*` à un seul sous-agent : c'est une consigne de la fiche de Gyna, pas une barrière. Un passage par jour à partir de 8 h (Paris), dans une conversation « Pilotage des pubs » créée par l'app. L'app dépose elle-même les visuels des pubs approuvées dans la bibliothèque d'images du compte (`syncAdImages`, `ad_images.meta_hash`, rendu par `get_ad_pilot` en `image_hash`) : l'outil de dépôt du serveur de Meta n'était pas disponible pour le compte. L'application Meta doit être en mode « En ligne » pour créer des pubs, et l'API publicitaire exige une version (`v26.0` par défaut). Suivi page `/campagnes` (`PilotDashboard`, `apps/web/src/lib/pilot-report.ts`) : dépense sur l'enveloppe, pré-inscriptions et coût, résultats par pub et par jour, lus chez Meta par l'app à chaque affichage, sans agent, et derniers gestes de l'agent tirés du journal. Non testé en conditions réelles au 13/10/2026.
- PostHog (décision du 20/10/2026, après une analyse où l'entonnoir du site a montré que la page, pas le pixel, limitait les pré-inscriptions) : serveur MCP `posthog` branché sur le profil par `GYNA_POSTHOG=1 bash infra/hermes/setup-hermes.sh` (clé personnelle PostHog **en lecture seule**, demandée sans affichage ; `GYNA_POSTHOG_URL=https://mcp-eu.posthog.com/mcp` pour un projet hébergé en Europe). Gyna et Campagnes le lisent pour les bilans et analyses (visites par `utm_source` et `utm_content`, parcours jusqu'à la pré-inscription) ; consigne de lecture seule dans les fiches, la clé en lecture seule étant la vraie barrière. Projet PostHog de L'Amorce : 277925.
- Accès invité « suivi des campagnes » (décision du 23/10/2026, pour Quentin, expert pub qui accompagne L'Amorce) : rôle `campaign_viewer` (`member_role`, migrations 0025 et 0026), en lecture seule. `current_org_ids()` exclut ce rôle, si bien que toutes les règles RLS existantes se ferment pour lui ; des règles de lecture dédiées (`current_viewer_org_ids()`) n'ouvrent que la venture, l'enveloppe (`ad_pilots`), les documents de campagne, les pubs (pas les posts) et leurs visuels, et le journal de l'agent Campagnes sur le pilotage. - Accès « prospection » (décision du 23/10/2026, pour Lauriane, assistante marketing ; connexion Brevo à venir) : rôle `prospector` (migrations 0027 et 0028). Elle voit le chat (ses conversations seulement, pas celles des associés), les prospects et les validations des messages de prospection (elle les valide elle-même) ; rien sur les pubs, posts, veille, campagnes ni skills. RLS dédiée (`current_prospector_org_ids()`, `current_org_ids()` l'exclut). Ses missions portent `missions.scope = 'prospection'`, imposé par la base (trigger `missions_set_scope`) : le serveur MCP refuse alors tout outil hors `PROSPECTION_TOOLS` (`packages/schemas`), le pont écrit `perimetre: prospection` dans le bloc de mission, et le plugin Hermes `gyna-mission` y bloque les outils Meta Ads et PostHog, pour Gyna comme pour ses sous-agents. Côté app : middleware limité au chat, aux prospects, aux validations et aux paramètres ; routes de pubs, de pilotage et de bibliothèque réservées à `session.fullMember`.
